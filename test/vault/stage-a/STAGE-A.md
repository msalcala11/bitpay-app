## 2. Proposed versioned schema — for review, not implemented

Keep one serialized `migration` record in the existing `bitpay.vault.migration` MMKV instance. Keep reference fields `status`, `wipeDone`, `initializing`, and the existing legacy `refresh` reader. Add one optional `repair` extension. Fixed source identifiers map to existing paths in code; there are no dynamic paths, wallet IDs, secrets or decrypted-value hashes.

```ts
// Design notation only. SourceDigest means SHA-256 of exact serialized source
// bytes, computed BEFORE decrypting; no actual digest values appear in this report.
type SourceDigest = string; // exactly 64 lowercase hex characters

type RepairV1 = {
  v: 1;
  generation: number; // integer 0..2147483647, local to this valid extension
  authority: {
    kind: 'default-mmkv-root';
    state: 'none' | 'active' | 'revoked';
  };
  historical?:
    | {state: 'staged'; legacySource: SourceDigest; targetWrite: SourceDigest}
    | {state: 'active'};
  async?:
    | {state: 'absent'}
    | {state: 'consumed'; digest: SourceDigest}
    | {state: 'unconsumed'}
    | {state: 'blocked'; reason: 'conflict' | 'required-undecodable' | 'changed'};
  temps?: {
    main?: {origin: 'optional-refresh'; digest: SourceDigest};
    bak?: {origin: 'optional-refresh'; digest: SourceDigest};
  };
};
```

All entries bind implicitly to the one current generation and fixed primary kind. **Active authority has no primary-content digest**: ordinary saves are allowed to change its bytes. `targetWrite` is only an interruption-proof marker for one *planned conversion*, not continuing authority. Its bytes are the planned GCM serialized root, not plaintext. It is removed on activation. This one-time staging design needs Stage A approval; if even a temporary conversion fingerprint is disallowed, cross-process activation without surviving original evidence must remain strict rather than inferred.

Validation is all-or-nothing: exact allowed properties/discriminants, valid digests, bounded integer, legal combinations and a proposed **1,024-byte UTF-8 extension bound**. Staged history requires generation zero, authority `none`, and no active receipts/intents. Active history requires active authority and generation zero. Revocation increments generation, sets `revoked`, and removes all dependent entries in the same record write. Generation greater than zero permanently prevents reissuing historical eligibility from an APP flag. Fresh strict reconciliation can establish new receipts/intents at that generation. Overflow stops before granting permissions; it never wraps.

For incomplete records, missing extension means no new permissions. Invalid/unknown-version extension means *the entire extension* is unusable: strict reference handling, no partial salvage, no automatic metadata reset. If fresh strict evidence permits a new extension, replace it with generation one (historical eligibility disabled), all fresh evidence, and verified write-back; no fragment supplies authority. A strict conflict, unreadable source without another legitimate basis, or absent required recovery source may still stop. Existing legacy `refresh` validation stays separate and strict.

For a valid completed base record, return through the existing key/base fast path **without reading or validating any new-extension member**. No new continuity, revocation, inventory or cleanup is run, even for malformed/unknown/oversized leftover repair entries. Existing enclosing JSON/status/wipeDone/initializing/legacy-refresh checks remain. Newly completed records omit `repair` in the existing completion write. `initializing` retains its separate reference lifecycle. Android's independent pending RKStorage checks still run as before; receipt machinery stays retired.

### Exact permission predicates

- **P (primary authority):** incomplete base, usable versioned key, usable extension in `active` state, and a consistent demonstrably loaded, valid modern default `persist:root`. Backups and temps never satisfy P. Retained key material is memory-only.
- **H (historical eligibility):** fully validated legacy CBC *MMKV primary*, literal `APP.migrationMMKVStorageComplete === true`, staged before conversion at generation zero; activate only after the planned modern root is verified. Neither modern flags nor the new importer issue H. A staged marker grants nothing by itself.
- **C (consumption):** exact decodable AsyncStorage bytes are validated and incorporated into, or permissibly superseded by, the verified modern primary using the existing strict coverage rules; the exact-source receipt is persisted/read-back verified before ordinary use. No attempted write, migration-start flag or importer flag suffices.
- **N (absence):** successful `getItem` returns `null`, P's primary has been independently verified, and the absence observation is persisted/read-back verified before later/cross-launch reliance. N is historical observation, not current absence or deletion authority.
- **Qualified unreadability:** required reads and key checks pass, P holds, and H/C/N supplies an unrevoked basis; a known blocked source cannot use these to mask its conflict. Return incomplete after the first rejecting AsyncStorage read; keep needed legacy credentials, stop AsyncStorage cleanup for this attempt, do not enter RKStorage cleanup.
- **Deletion:** successful current source read matches the specific consumed receipt or optional-temp intent, P still holds, and identity is rechecked before removal. Recheck after every relevant await, including rejection. A changed source loses its old permission. Verify removal; unresolved verification cannot complete. A matching digest without P never disposes of a sole recovery source.
- **Optional intent:** current verified modern primary plus the reference optional-refresh prerequisites, exact planned temp bytes, persisted/read-back-verified intent *before* writing the temp. A `.bak` refresh intentionally retains the previous valid main backup under the existing rotation policy; it need not equal the current primary. That origin makes it optional, not its contents being equal to current data.
- **Undecodable source:** preserve the reference immediate-discard rule, including a nonempty protected projection and subsequent active-source checks. No consumption receipt or durable damaged-source disposal permission. Record only unconsumed/blocked observation as appropriate, not a hash of unstructured potential plaintext. Retrieval alone grants no startup basis. Once the last protected field is removed, readable undecodable bytes remain a strict stop. Existing immediate-discard paths with a validated selected backup do not acquire a new primary-only requirement.
- **Completion:** unchanged real base prerequisites, all source obligations resolved by current evidence, scrub verified, needed legacy credentials retired/absent. No unreadability, inconclusive primary, failed permission write or pending deletion can be called complete. RKStorage has its separate marker/prerequisites.

## 4. Wrapper-only observations, persistence and hard limits

### Observation algorithm for applicable pending permissions

After key validation, synchronously sample **two key lists, two logical sizes, two root strings and one `contains(ROOT)`** (seven public wrapper calls), without an intervening await. Require safe nonnegative integer sizes no larger than the pinned signed-int wrapper limit; consistent lists/sizes/strings and accessor presence. Exceptions, inconsistencies and zero-key/zero-size samples are B. At least one key or a valid positive logical size establishes a loaded *view*, not newest data. In such a view, consistent absence, non-string presence or a recognized snapshot-validation failure is A. Arbitrary runtime/crypto-engine exceptions are B, not proof of invalidity; Stage B must retain typed validation failures and cannot classify errors by native message substrings. If the pinned crypto boundary cannot safely distinguish authentication failure from runtime failure, use the conservative observation-failure path and report that additional availability limit.

No physical-length/header/checksum observation is used to break ties. The scrub's already-authorized metadata checks remain confined to the unchanged scrub algorithm. No write probes, trim, clear, recrypt, instance recreation, teardown or new restart action is a continuity observation. New JS wrappers and module reloads do not reset the native load condition.

A guarded context is installed only after incomplete preparation grants actual permissions and is cleared on completion. Preparation and importer entry validate the platform key before possible revocation. Pending ordinary get/set/restore-entry gates reuse that preparation context for normal healthy checks; a prospective revocation outside preparation revalidates the platform entry and rechecks the observation before persisting the tombstone. An in-memory detecting-attempt latch prevents a later supported write from hiding the observed loss. For active pending contexts, use the already-observed validated root for the read path and make any observation failure escape before the existing fallback catch; never feed a failed observation into restore. Guard the primary write entry and any sanitizing rewrite. Gate failures must escape the adapter's existing fallback catch; `restoreFromBackup` itself remains untouched. Completed/fresh/non-permission paths acquire no new observation gate. This small adapter-entry change is specifically for pending permissions, **not a repair of the reported ordinary restore hazard**.

### Precise guarantees and limits

- R means **persisted through the public API and read-back verified in the mapped view**. It is not forced flush, cross-store atomicity, power-loss durability, or proof of process-death survival. Avoid unqualified “durable.” Normal wrapper teardown explicitly syncs; normal reopen tests cannot establish unsynced-crash guarantees.
- Multi-write transitions above expose their partial states: staged record → root write → active record; intent → temp write → target replacement → slot resolution; receipt → deletion → verification → observation/receipt update. Every incomplete boundary keeps permission ungranted or cleanup unresolved. Stage B must interrupt after each call and separately test fresh native processes. Inside-native kills and power loss remain separate unaccepted risks.
- Successful revocation R prevents restored/recreated primary contents from reviving its old generation under a subsequently readable record. A failed revocation write is a stop, not successful revocation. An optional intent write may defer only if the previously verified whole record can be revalidated unchanged, no new temp was written, and startup does not depend on the failed new grant; otherwise it stops as permission persistence failure. The same-process latch helps, but an old active record plus a restored primary after failed persistence/realm loss is indistinguishable from no recorded loss. **An unconditional non-revival guarantee across that case cannot be established inside this scope.** Do not silently claim it or add a journal/native sync to obtain it.
- A metadata-store failed load may hide an existing record behind apparent absence. There is no permitted global metadata-load gate or new backend. New machinery can act only on readable, validated metadata; apparent absence proves neither fresh installation nor absence of earlier revocation. Strict fallback must not invent handover/H from missing fragments. It still cannot detect a hidden prior lineage. Absolute receipt/revocation guarantees in that condition require an out-of-scope observation/persistence change and are a Stage A review limitation.
- Zero/zero can mean never-written, failed load, genuine loss or discarded invalid contents. While active permissions are pending, the prescribed B policy blocks reference backup restoration even when a good backup survives. Persistent genuine loss can remain blocked in every new process. Reopening guidance is conditional; Retry cannot reload the pinned cached failed view. Completed-base restore behavior is preserved.
- Nonempty views cannot establish newest data. Native silent fallback, valid-snapshot rollback, external replacement and loss concealed before observation remain undetectable. No acceptance of these or the original compaction/power-loss residuals is inferred.
- Record separately, without changing/investigating further: the reported checksum-file-open failure may accept an ordinary restore write; source inspection confirms the reference adapter can call `restoreFromBackup` on an absent/read-failing primary and that helper writes to MMKV. The supplied native run was not accessible; the downstream full-app effect and whether backup carries the app through are **not demonstrated here**.
- If the required contract treats failed-revocation persistence or hidden-metadata cases as unconditional guarantees rather than these observable-state limits, Stage B is blocked on that precise contract conflict. No stronger mechanism is proposed for automatic implementation.

## 5. Bounded work and report policy

- AS calls per attempt: at most **one initial get**, **one pre-delete get**, **one post-delete get**; at most one `removeItem`. Initial qualified rejection stops AS work at one read; pre-delete rejection at two; post-delete rejection at three. No polling/retry inside the attempt. A changed recheck invalidates permission and stops instead of restarting classification. Single-flight preparation remains.
- Observer: exactly seven wrapper operations per full sample (fewer only on an early throwing read), no sampling retry. Inconclusive initial observation performs no source inventory/mutation. Later samples bracket the existing awaited boundaries and immediately precede permission writes, deletion, promotion, primary writes and bootstrap. Proposed accounting: `7 × (entry samples + 2 × guarded awaited boundaries + synchronous commit gates)`, all reported separately from existing scrub reads; Stage B must instrument and assert the actual call graph rather than claim a guessed global number. For review, set a conservative per-preparation ceiling of **400 observer samples / 2,800 wrapper observation calls**, excluding pre-existing non-observer reads. The static envelope is at most 143 filesystem boundaries (10 initial reads, 28 required/temp handling, 30 refresh, 23 cleanup, 4 backup selection, 36 unchanged scrub measurements, and 12 extra identity rechecks), four AS boundaries and eight key boundaries; two samples per boundary, up to 24 record-commit gates, 18 scrub guard callbacks and 40 entry/phase gates remain below 400. Mutually exclusive branches make this an upper envelope, not a typical workload. Stage B must assert that envelope against its final call graph and stop for review if it cannot satisfy it, not silently enlarge it. This is a bounded composition of fixed source paths, one pass per slot, and the unchanged bounded scrub. Native side effects of reads are outside the application-mutation counter.
- New record-extension writes: **at most ten per attempt**, from at most one historical staging, one activation, one source permission issuance, two temp intents, three verified slot/observation resolutions, one batched source withdrawal, and one completion write. Revocation exits and replaces remaining work, rather than adding another cleanup pass. Coalesce compatible changes; skip byte-identical records. A new conversion encoding after an interrupted pre-write stage may require a changed intent, not an unchanged-write loop. Generation and fixed slots do not grow with launches.
- Persistent qualified rejection on a stable modern pending state: no new metadata write once the needed basis is already recorded; no AS cleanup after rejection; no RK cleanup. Unresolved exposure and shared AS functionality remain honest limitations. No whole-app-health guarantee.
- Aggregate safe deferrals in one preparation result. Emit at most one report per preparation; remember only the last fixed diagnostic signature in memory, suppress identical concurrent/same-process retries, permit materially different code/reason/phase/source sets. No persistent report history or source digests in the signature. Cold processes may each emit one report.
- Reference measurement on Node 22/macOS, Android boundary model: three pending calls use three AS reads each, field decrypt calls 50/30/30, reducer decrypt calls 10/6/6, MMKV string reads 53/35/35, and record writes 2/0/0. Each emits two reports. These are primitive decrypt-call counts, **not** whole-snapshot decoder counts or phone timings. Exact per-case milliseconds and counts are in `results.json`. Stage B must measure the approved observer/permission paths, including indefinite rejection and inconclusive loss.
- Operation counts cannot bound a native hang. No timeout may release ownership while native work continues.

## 6. Diagnostics and smallest native-Alert design

Replace migration substring routing with explicit, typed code/reason/actual-phase/fixed-source/capture-origin metadata in the existing identity-based WeakMap. Capture-site origins are a fixed enum. Distinguish key missing/read/backend/format failure; base-record read/JSON/reference-field failure; unusable extension/strict fallback; primary read/inconclusive/recognized invalidity; AS inventory/recheck/verification rejection; unconsumed/revoked conflict; observed authority loss; permission write/read-back failure; replacement failure; pending cleanup. Do not label a read rejection as a required copy write or every promotion failure as refresh.

Unknown thrown objects get a fixed capture-site classification. Never inspect native messages, names, arbitrary code properties, prototypes, causes or getters. Preserve known classifications through wrappers by identity. Create a fresh bounded display identifier and emit a fixed event payload with no original exception/stack (or an equivalently scoped no-stack capture); do not let SDK exception handling reattach native input or sensitive paths. Removing only a stack's first line is insufficient. Startup reporting is once per failed preparation, with retry aggregation as above. Unusable optional metadata need not generate a fatal event when strict fallback succeeds.

Keep the existing native `Alert`; no React replacement, splash hide, new screen, process restart or destructive action. Propose a small startup-only controller, owned by the existing `ReduxProvider` effect, with failure state independent of visibility, an attempt/dialog generation, one visibility flag, one pending support action, and one removable AppState subscription. Two buttons only: localized **Retry** and **Help & Support**. Message includes localized “Do not uninstall or clear app data”; “If Retry does not help, fully close and reopen the app. This may not resolve the problem”; and a short fixed diagnostic ID. Use the initialized i18n singleton and `URL.HELP_AND_SUPPORT`, without Redux/navigation. No clipboard action is needed.

Retry dismisses/invalidates the old failure before starting exactly one new attempt; success clears failure and queued callbacks/listeners. Support dismissal retains the failure; linking settlement and return-to-active events schedule one guarded native re-presentation. Handle rejection while still active and the case where opening support produces no background edge. Dismiss callbacks must not reopen during Retry/support launch or after success. Use one scheduled presentation, not polling; actual event ordering must be verified in Stage B. Component cleanup cancels obsolete callbacks and removes the listener. The normal splash/navigation path is untouched.

The candidate invalid-cache seed was reproduced **only in the mocked production preparation path**: no application writes/key/record on failure, then same-process success after external fixture removal. Stage B must seed a disposable install externally, verify Alert visibility over normal splash, support success/return and opening failure, reachable Retry and real same-process recovery. Headless Hermes and this seed test do not certify rendered UI. No production failure switch/test hook is proposed.
